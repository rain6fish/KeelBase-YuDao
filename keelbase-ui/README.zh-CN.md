# keelbase-ui —— 这个宿主渲染用的视觉层

这些文件就是 KeelBase 视觉层：产品自有前端所用的那套 Element Plus 令牌（颜色、圆角、字体）。
把它们放在这里，是为了让**宿主的界面**能按我们的样子渲染，而**不改动任何一个上游文件**。

## 它们是一份生成出来的副本

令牌只在 `Web-Admin-Vue` 里写一次：

    Web-Admin-Vue/src/styles/element-theme.scss
    Web-Admin-Vue/src/styles/themes/{_blue,_teal,_graphite}.scss

要改**去那里改**，然后重新入库并校验：

    bash scripts/sync-ui-theme.sh          # 写入副本
    bash scripts/sync-ui-theme.sh --check  # 只校验；漂移即非零退出

副本必须保持逐字节一致（换行已归一），**不要就地编辑这些文件**——`--check` 存在的意义就是逮住这件事。

## 这些令牌是什么

纯 CSS 自定义属性，由 `<html data-theme>` 与 `<html class="dark">` 驱动：三套可切换主题
（深靛默认 / 青绿 / 石墨）× 亮暗两态。这里没有任何东西会编译成构建期变量，所以这一层可以**在应用
自己的样式表之后**再放进去、在运行时生效——上游的 SCSS 一行都不用改。

在本宿主里**只有默认（深靛）那套是活的**：应用没有 `data-theme` 切换器，故 `teal` 与 `graphite`
两段永远不会命中。它们仍随副本一起带过来，好让三套主题保持「一份被撰写的东西」，而不是分叉。

## 两张样式表，两件事

| 文件 | 覆盖什么 |
|---|---|
| `theme/element-theme.scss` → `keelbase-theme.css` | **Element Plus 令牌面**——颜色、圆角、字体、卡片与按钮的处理 |
| `theme/host-yudao.scss` → `keelbase-host.css` | **yudao 自己的布局命名空间**——`--left-menu-*` · `--top-header-*` · `--logo-*` |

后者之所以存在，是因为前者够不到侧边栏、顶栏与标签条：yudao 用一套自己的命名空间驱动这三者，默认成
产品并不使用的深藏青。它是**翻译，不是拷贝**——`Web-Admin-Vue` 把这同一套样子陈述在（`.admin-aside` ·
`.el-menu-nav`）这些在这里并不存在的类名上，故那些规则无法入库。其中每一个**取值**都是对已入库令牌的
`var(--el-*)` 引用，于是配色仍然只有一个源；被重述的只是结构。它在本仓撰写，不参与同步。

## 这一层怎么铺上去

**构建期注入**——视觉层只存在于产物里，从不进入源码。

    bash scripts/build-host-ui.sh              # 按需拉取、装依赖、构建、注入
    bash scripts/build-host-ui.sh --skip-build # 在已有的产物目录上注入

构建所用的检出始终不会被改动。代价是：界面自己的开发服务器（dev 模式）渲染的仍是上游的样子；
只有构建产物带着这一层。

注入的链接带**内容哈希**（`keelbase-host.css?v=…`）。Vite 给自己的产物做了哈希；这两个文件名字是固定
的，故不带上版本号时，浏览器缓存过的那份在视觉层改了之后还会继续被用——表现出来就是「改了跟没改一样」。

侧边栏也落在产品自己的行距上：一级 42px、二级 38px，并在右侧留出余白，使菜单项不会跑到滚动条下面——
这里的滚动条是**浮**在内容上的，而不是占一条留白。

**构建还关掉一样东西。** 上游在多数页面上渲染一条文档提示条，指向它自己的文档站。它由一个构建期
开关（`VITE_APP_DOCALERT_ENABLE`）控制，故构建通过环境变量把这个开关置掉，而不是用 CSS 把提示条
藏起来——元素因此根本不渲染。Vite 让已存在的环境变量优先于 `.env` 文件，这正是让这件事停留在
「改构建开关」而**不是**改上游文件的原因。用 `KEELBASE_YUDAO_UI_DOCALERT=true` 可恢复上游行为。

## 在本地看这一层

这一层在**产物**里，所以要看它就得把产物服务起来。光把文件服务出去不够：产物**故意**把接口打成
**同源**（构建清空 `VITE_BASE_URL`，页面于是问服务它的那个主机，而 `/admin-api` 去哪由外层 nginx
决定）。在部署的机器上这正是要点；在本地，这意味着一台普通静态服务器会把每个接口请求都用 SPA 兜底
接走——返回 `index.html`、状态码 200——而应用把它当成一次成功响应，只是响应体里没有数据。登录于是
报出一个既不提接口也不提代理的错误，看上去像是客户端的问题。

`scripts/serve-host-ui.mjs` 补上这一环：根路径是静态文件，转发规则与部署的 nginx 相同
（`/admin-api`、`/app-api`、`/app`、`/ai`、`/audit`）到指定的后端。接口路径**绝不**用 SPA 兜底作答；
够不到后端的接口调用**如实报错**（502）——于是下一个症状绝不会是一次安静的空响应。

    node scripts/serve-host-ui.mjs                        # 页面在 :18099，后端 http://127.0.0.1:48080
    node scripts/serve-host-ui.mjs --port 18100 --backend http://127.0.0.1:48080

## 与 RuoYi 宿主不同的两条事实

1. **界面不在本仓。** 上游把 `yudao-ui/yudao-ui-admin-vue3` 留成占位目录，故构建脚本把真正的树
   拉到 `target/`——那是上游 `.gitignore` 已忽略的路径，因此**没有为把它挡在索引外而改动任何受
   跟踪文件**。

2. **应用在挂载时把自己的主题色写成 `<html>` 的内联样式**（`ConfigGlobal` → `appStore.setCssVarTheme()`）。
   内联样式本身就压过普通样式表，所以「最后链一个 CSS」能带上**除主色族以外**的一切。`!important`
   能压过非重要的内联样式，故构建只给那一个族加上它——其余层保持在运行时可被覆盖，宿主的主题选择器
   对别的部分照常有效。**副作用**是：宿主自己的主色选择器不再能明显改变页面——这一层是**刻意**把主色
   钉住的。

## 有三类增量，注入层表达不了

样式表能重绘宿主渲染出来的东西，改不了宿主**照着源码**渲染出来的东西——而本产品需要的三件事恰恰是后者：
首页那张卡片的内容是组件里一个写死的数组，logo 是一句源码里的 import，IM 模块则**根本不发**。故三者都作为
**增量**承载，在构建前铺到检出上。

    keelbase-ui/host-overlay/      我们**新增**到检出里的文件
    keelbase-ui/host-patches/      应用到检出上的补丁
    keelbase-ui/host-removals.txt  我们从检出里**拿走**的路径

检出是一次性的、每次重新取，故构建先把它复位到上游，再把增量铺上。三个方向都**刻意**响亮地失败：覆盖的
文件在上游被挪走、补丁应用不上、清单点的路径已不在，都意味着我们的增量需要重做——而不是跳过它，那会让产物
悄悄变成半我们的。

**覆盖目录只增不替。** 这正是让耦合保持响亮的原因：我们新增的文件只被补丁引用，故上游一旦挪动引用它的那段
代码，补丁就应用不上并会明说。替换则没有这样的绊线——上游把文件改名后，我们那份会静静躺在那里不被用，而
应用继续用它的。

**拿掉一条路由与拿掉那些文件是两件事，两件都得做。** 路由是**补丁**的活：它按字面路径 import 那些文件，留着
它构建就会失败。文件是**清单**的活；而把它们放进产物的**不是**路由，是 `utils/routerHelper.ts`——它用
`import.meta.glob('../views/**/*.{vue,tsx}')` 把每个视图都收进来，好让后端菜单能按路径点到某一个。只删路由，
IM 模块照样会被构建、被部署出去；两条路都够不到它，这正是代价始终只是那点字节的原因。

## 图标，以及它们原先来自的那个 CDN

控制台渲染 Iconify 图标，而上游只注册了三个集合（`ep`、`fa`、`fa-solid`）。交给它的其余每一个图标，
它都在**运行时**从 Iconify 的公共 API 取——`api.iconify.design` / `api.simplesvg.com`——于是每位访客
的浏览器都在访问一个这里没人控制的主机。那是厂商痕迹，而且是一次请求，不只是字符串。

两处改动把它关掉。Icon 组件改为从 `@iconify/vue/offline` 导入，那份包里根本没有任何 fetch；产品真正
渲染的图标则收进一个随页面发出的集合。

    node scripts/gen-offline-icons.mjs           # 写出 keelbase-ui/host-overlay/src/assets/keelbase-icons.ts
    node scripts/gen-offline-icons.mjs --check   # 只校验；有漂移则非零

生成器扫描检出源码里的图标引用（故检出须带着我们的增量——先跑一次构建）。上游树跨约 35 个集合，整套
打包要加约 70MB，故只保留被引用的那些（约 250 个图标、约 100KB）。`host-icons-extra.txt` 列出少数来自
**数据**的图标——数据库菜单行带一个图标名，扫源码看不见。构建在装依赖之后跑 `--check`，于是上游日后新增
的一处图标引用会让构建失败，而不是渲染成空白——在离线组件下，漏注册就长这样。

**两份构建不共用注册表。** `@iconify/vue` 与 `@iconify/vue/offline` 各留各的 `storage`，故
`addCollection` 必须与组件来自同一个入口——因此 `plugins/svgIcon/index.ts` 也从 `.../offline` 导入它。

## 头像与品牌标记

`assets/keelbase-avatar.svg` 由 [DiceBear](https://www.dicebear.com) 生成（`shapes` 风格）。它**自带
的元数据**声明该图形为 **CC0 1.0**；其所在包声明 MIT。两者都可用于商业用途，归属写在 `NOTICE` 里。

它是通过**样式表**而不是组件铺上去的，这正是让一条规则覆盖控制台里**全部**头像的原因——含表格里与个人页
里的那些——而不必逐个去改。宿主发下来的图被藏起来，由它下面那层承载我们的；`src` 从这里够不到，换不掉。

`host-overlay/src/assets/imgs/keelbase-logo.svg` 是产品的品牌标记，路径与颜色都与 Web-Admin-Vue 自己的
logo 组件和 favicon 相同，于是这个标记仍然只有一个源。

## 本部署显示的那几个名字

系统名取自构建的环境变量（`VITE_APP_TITLE`），故它落到页面标题与界面里每一处会打印它的地方，而**不改任何
源码**。

另有两个名字**不是标签**，在这里改不了。**租户名**是登录**按名字查租户**时用的那个；内置管理员的**昵称**是
顶栏与问候语显示的那个。两者都在数据库里，且登录表单预填的值必须与租户记录一致，否则登录就用不了。它们**一起
动**，走 `sql/keelbase-brand-names.sql`——已有库在上游种子之后跑它；新装则先跑上游种子，再跑它。

上游那份种子**一字不改**：它是上游的、几千行、且在多个方言间重复；改名该放在一份**说明它改了什么**的文件里，
而不是散落在他们那份里的编辑。

## 两处坑，构建踩过才知道

**href 必须是绝对路径。** 相对 `href` 是相对**当前路由**解析的，不是文档根。应用走 history 路由，
所以在根路由下它是对的——而那正是所有人第一个会看的地方——用户一到深层路由，链接就指向一个不存在的
路径，**整层静默消失**：不报错、也没有用户看得见的 404，只是上游的样子又回来了。构建现在从 Vite 已经
产出的资源链接上读出 base 前缀，写出绝对 href。

**单靠 `!important` 压不过 yudao 自己的菜单规则。** 那些规则带作用域，形如
`.v-menu[data-v-…] .el-menu .el-menu-item:hover`——五级类权重。而
`html body .el-menu .el-menu-item:not(.is-active):hover` 只有四级，因为 `:not()` 只贡献其**参数**的
权重；两边都是 `!important`，于是 yudao 胜，它那句白字悬停又回到浅色底上。适配层在这些选择器里带上
一个 `.v-menu` 祖先，为的就是这份权重。**改它之前先知道这件事**：删掉一个看着多余的类名，那个状态就会
**静默**地又坏掉。

**选择器列表是不容情的。** 浏览器解析不了其中**一个**选择器，它所属的**整条规则**就作废，而且**悄无
声息**——同一条列表里其余本来正确的选择器也一并失效，没有任何东西会报出来。`sass` 对嵌套的 `:has()`
照编不误，而嵌套 `:has()` 本就不允许，于是一条把它与一个完全正确的选择器并列的规则，两个都丢了。适配层
因此**一条规则只写一个选择器**，让每条规则各自独立地成立或失效。那些重复是刻意的。
